# pi-subagents

`pi-subagents` передаёт отдельные задачи дочерним агентам Pi. Это удобно для review кода, разведки, реализации, параллельных проверок, сохранённых workflow и фоновой работы.

## Что это за форк

Это независимая линия [`pi-subagents`](https://github.com/nicobailon/pi-subagents) для `datspike/nb-pi-subagents`.
Здесь выборочно переносятся полезные изменения upstream и развиваются собственные решения. Форк не обязан оставаться точной копией или последовательностью патчей к одной версии upstream.

Основная модель делегации сохраняется: обычные и фоновые дочерние запуски, встроенные агенты, сценарии, цели, FleetView, watchdog и extension API.
Главные направления форка:

| Направление | Что меняется для пользователя |
|---|---|
| Контекст для модели | Поверхность делегации остаётся компактной, а подробные инструкции выдаются ограниченными порциями, когда они нужны. |
| Справка для агентов | `subagent({ action: "guide" })` и `/subagents-guide` отдают справку по теме и разделу с ограниченным объёмом. Она работает и без skill пакета. |
| Границы доверия | Если проекту нельзя доверять, его настройки, агенты, цепочки, пакеты и навыки не используются. `agentScope: "project"` завершается с отказом; источники пользователя и встроенные источники остаются доступны. |
| Результаты и восстановление | Прогресс, состояние, завершение, intercom и сохранённые просмотры расшифровок ограничены по размеру. Усечение сохраняет полезные метаданные и явно помечает неполный текст. Ошибка сохранения результата или артефакта не маскируется под успешный результат. |
| Надёжность запусков | Для каждого запуска `leases` и последовательные публикация, продвижение и вывод результата из обращения защищают новые данные от устаревших или заменённых. Отсоединённые и приостановленные запуски сохраняют сведения для восстановления. |
| Проверка и оценка | Метаданные проверки и средства управления дочерними командами проходят через делегацию, но внутренние поля проверки и оценки не попадают в схему для модели. |

Форк может расходиться с оригиналом и позже выборочно переносить новые изменения upstream. Проверяй документацию и примечания к выпуску установленной версии: этот раздел описывает направление форка, а не обещает постоянную уникальность.

## Установка

```bash
pi install git:github.com/datspike/nb-pi-subagents.git
```

Этого достаточно. Фоновые дочерние запуски используют SDK хост-системы: npm Pi сохраняет отдельный исполнитель Node, а официальный автономный выпуск Pi 0.86.1 для Linux x64 загружает тот же исполнитель через встроенный SDK Pi. Поддерживаемые границы и проверка описаны в [Standalone background execution](docs/standalone-background.md).

## Первый запуск

Не нужно заранее создавать агентов, писать конфигурацию или учить slash-команды. После установки достаточно попросить Pi обычными словами:

```text
Используй reviewer, чтобы проверить этот diff.
```

```text
Попроси oracle проверить мой план. Пусть он оспорит допущения и скажет, что я мог упустить.
```

```text
Попроси scout разобраться в этом коде с учётом нашей беседы, а затем задать мне уточняющие вопросы.
```

```text
Запусти параллельные проверки: корректность, тесты и лишняя сложность.
```

Этого достаточно. Pi сам решает, вызывать ли `subagent`, какого агента выбрать и как собрать работу.

## Как это работает

Pi — родительская сессия. `subagent` — отдельная дочерняя сессия Pi со своей задачей.

После запроса на делегацию Pi запускает дочернюю сессию, передаёт ей задачу и возвращает результат. Обычные дочерние запуски работают внутри процесса родительской Pi и показывают ход работы в беседе. Фоновые продолжаются в отдельном процессе и остаются доступными для проверки.

Установка расширения сама по себе не запускает reviewer в фоне. В новой сессии Pi сначала может показать небольшой загрузчик `subagents_enable`, а полный инструмент `subagent` станет доступен после разрешённой делегации. Для других моделей `subagent` доступен сразу, чтобы не ломать кэш подсказки. Настройка [`toolActivation`](docs/configuration.md#toolactivation) меняет это поведение: она управляет режимами `auto`, `dynamic` и `eager`. После вызова `subagents_enable` инструмент появляется со следующего запроса модели. Сложность задачи сама по себе не даёт права на делегацию. `bg_wait` и ответы supervisor доступны и без активации.

Если каждую реализацию нужно проверять, укажи это в задаче или правилах проекта:

```text
После реализации всегда запускай reviewer.
```

## Встроенные агенты

Расширение сразу поставляет несколько ролей:

| Агент | Когда использовать |
|---|---|
| `scout` | Быстро найти нужные файлы, точки входа, поток данных и риски. |
| `researcher` | Найти внешнюю документацию и источники. Нужен [pi-web-access](docs/agents.md#web-research-prerequisites). |
| `evidence-auditor` | Независимо проверить утверждения и источники готового research brief. Нужен [pi-web-access](docs/agents.md#web-research-prerequisites). |
| `worker` | Внести согласованные изменения, проверить их и передать родителю нерешённое решение вместо догадки. |
| `reviewer` | Проверить реализацию, тесты, крайние случаи и лишнюю сложность; при необходимости внести небольшие исправления по задаче или плану. |
| `oracle` | Получить второе мнение до изменения и оспорить допущения; файлы он не редактирует. |
| `delegate` | Передать общую задачу агенту, который работает близко к родительской сессии. |
Практическое правило: сначала `scout`, затем `researcher` для внешних фактов, `evidence-auditor` для важных утверждений, `worker` для реализации, свежий `reviewer` для проверки и `oracle`, когда нужно оспорить решение.

## Типовые сценарии

В пакете есть `/council` и `council-mode`, а также примеры профилей `council-*`, которые можно добавить в свой каталог агентов.

| Что нужно | Как попросить |
|---|---|
| Второе мнение | «Попроси oracle проверить этот план и найти слабые места». |
| Сложная диагностика | «Используй oracle, чтобы изучить ошибку до изменения кода». |
| Проверка diff | «Попроси reviewer проверить этот diff». |
| Несколько проверок | «Запусти reviewers для корректности, тестов и очистки». |
| Обсуждение решения | «Используй `/council`, чтобы сравнить варианты». |
| Реализация и проверка | «Реализуй это, затем проверь результат». |
| Повторная проверка | «Повторяй проверку, пока не останется проблем, но не более 3 раундов». |
| Исполнение утверждённого плана | «Пусть worker реализует согласованный план, затем запусти свежих reviewers и примени их замечания». |
| Разведка перед планом | «Попроси scout изучить поток авторизации перед планированием». |
| Фоновая работа | «Запусти это в фоне». |
| Сохранённый сценарий | «Запусти сохранённую цепочку проверки в этой ветке». |
| Список агентов | «Покажи доступных subagents». |
| Текущие запуски | «Покажи активные async runs». |
| Проверка настройки | «Проверь, правильно ли настроены subagents и intercom». |

Для реализации обычно подходит цепочка `clarify → scout → worker → свежие reviewers → worker`. Готовые `/parallel-review` и `/review-loop` описаны в [Workflows](https://github.com/datspike/nb-pi-subagents/blob/main/docs/workflows.md).

## Где видна работа

Обычные запуски показывают ход работы в беседе. Фоновые продолжаются после возврата управления.

В TUI под редактором есть FleetView с текущими запусками. `/subagents-fleet` открывает подробный просмотр: там можно изучить дочерние запуски и расшифровки, направить или остановить запуск. Можно также попросить Pi: «Покажи текущие async runs».

Подробнее об артефактах запусков и наблюдаемости — в [Observability](https://github.com/datspike/nb-pi-subagents/blob/main/docs/observability.md).

Для ограниченного управления запусками `maxSubagentSpawnsPerRun` задаёт общий лимит дочерних запусков в одном дереве. По умолчанию он равен 64 и не смешивается с текущим числом параллельных запусков и общим лимитом создания дочерних запусков для сессии. Подробности — в [Configuration](https://github.com/datspike/nb-pi-subagents/blob/main/docs/configuration.md#maxsubagentspawnsperrun).

## Если что-то пошло не так

```text
/subagents-doctor
```

Или попроси: «Проверь, правильно ли настроены дочерние агенты и intercom».

Для справки по установленной версии используй `/subagents-guide [topic]` или `subagent({ action: "guide", topic: "workflows" })`. По умолчанию открывается `overview`. Доступны темы `overview`, `workflows`, `agents`, `missions`, `observability`, `tool-reference`, `configuration`, `models`, `watchdog`, `extension-api` и `council`.
