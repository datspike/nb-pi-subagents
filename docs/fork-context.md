# Контекст форка

Это рабочая линия `datspike/nb-pi-subagents`, а не нейтральная копия `nicobailon/pi-subagents`.

## Локальные правила

Текущая задача пользователя, `AGENTS.md` и `VISION.md` задают правила работы. Они определяют, что строить, что отклонять и какое `evidence` считать достаточным.
Форк может сохранять поведение upstream, но его тексты, настройки по умолчанию, привычки работы и предпочтения продукта — только справочный материал. Они не становятся нашими правилами автоматически.

Если источники расходятся, явно разделяй:

- **`evidence`** — проверенный факт из кода, теста, вывода команды или названного первичного источника.
- **`inference`** — вывод, который ещё нужно проверить.
- **`unknown`** — решение или поведение, которое пока не установлено.

Не превращай личную память, старую беседу, один сбой или предложение upstream в правило репозитория, пока не выделены устойчивый принцип и его область действия.

## Как работать

Для любого изменения в этом форке:

1. Сначала назови результат, который увидит пользователь. Потом выбирай механизм.
2. До нового пути проверь существующий код, потребителей, тесты и документацию.
3. Выбирай самое маленькое изменение, которое доказывает нужный инвариант. Не расширяй public API, хранение данных, жизненный цикл или запуск без отдельного основания и `evidence`.
4. Считай тесты и вывод команд доказательством поведения. Документация задаёт правила для будущей работы, но сама по себе не доказывает работу кода.
5. Сохраняй контроль оператора: работу нужно видеть, ограничивать, возобновлять и честно описывать остаточный риск.
6. Существенные решения и их причины записывай в подходящий проектный или рабочий документ. Не переноси в tracked files историю личных сессий и credentials.

## Как читать upstream

Код, тесты, issues и документация upstream помогают понять совместимость и доступные примитивы.
Они не задают цели форка, его планку качества, стиль инженерной работы и критерии приёмки.
Переноси изменение upstream только после проверки, что оно служит правилам форка и не возвращает незаметно отвергнутый путь.

Для контекста модели используй порядок:

`локальные правила → краткий бриф форка → проверенные code/tests/docs → текущая задача → evidence`

Дочернему агенту передавай только нужный фрагмент. Окончательную проверку результата по локальным правилам выполняет родитель.

## Граница слоя

Этот слой объясняет, как понимать и проверять работу в форке.
Он не заменяет public tool schema, child launch contract, persistence format, lifecycle rules и compatibility tests upstream.
Для изменений этих поверхностей сохраняются действующие правила одобрения и проверки.
